# Desk Analytics - AWS Infrastructure

Terraform-managed infra for the Desk Analytics app: VPC, ALB, EC2, and RDS PostgreSQL.

## Architecture

```
Internet → ALB (public subnets, :80) → EC2 (public subnet, :3000)
                                              ↓ :5432
                                     RDS Postgres (private subnets)
```

- VPC: 1 VPC, 2 public + 2 private subnets across 2 AZs.
- EC2: 1 instance running the app via Docker Compose (installed by `user_data` on boot).
- RDS: PostgreSQL in private subnets, not publicly reachable.
- ALB: fronts the app on port 80, forwards to EC2 on port 3000.
- Security groups: ALB accepts from internet → EC2 accepts only from ALB (+ your IP for SSH) → RDS accepts only from EC2. No tier is reachable except from the one in front of it.
- State: stored remotely in S3 (encrypted, versioned), locked using S3's native locking (`use_lockfile`) - no DynamoDB table needed.

## Setup

1. Create the S3 state bucket (one-time, see comments in `backend.tf` for the exact CLI commands - enable versioning + encryption).
2. Copy and fill in variables:
   ```
   cp terraform.tfvars.example terraform.tfvars
   ```
   Set `key_pair_name` (must already exist in AWS) and `allowed_ssh_cidr` (your IP, e.g. `1.2.3.4/32`). Everything else has sensible defaults.
3. Deploy:
   ```
   terraform init
   terraform plan
   terraform apply
   ```
4. Grab the outputs you'll need for CI/CD secrets:
   ```
   terraform output
   ```
   `rds_endpoint` → `DB_HOST`, `alb_dns_name` → `ALB_DNS_NAME`, `db_password_secret_arn` → `DB_SECRET_ARN`.
5. Access the app at `http://<alb_dns_name>` (not the EC2 IP - see Security below).

## Architecture decisions

- One EC2 instance, no Auto Scaling - kept simple/cheap for an assignment. A crashed instance needs manual replacement; a crashed *container* self-restarts (`restart: always`).
- ALB in front of a single instance - mainly for the stable public entry point and health checking, not for horizontal scaling here.
- No NAT Gateway - private subnets only host RDS, which needs no outbound internet, so a NAT Gateway would just add cost with no benefit.
- Elastic IP on EC2 - keeps the SSH/deploy address fixed across instance stop/start.

## Security considerations

- Network isolation: RDS is in private subnets with `publicly_accessible = false`; each security group only trusts the tier directly in front of it.
- SSH: restricted to `allowed_ssh_cidr` - as this is dummy project set it to `0.0.0.0/0`.
- Encryption at rest: EC2 root volume (gp3, encrypted) and RDS storage are both encrypted.
- Secret management: the DB password is generated by Terraform (`random_password`) and stored in AWS Secrets Manager - it's never in `terraform.tfvars`, never in Terraform state as a plain variable, and never in a GitHub secret. The EC2 instance reads it at boot/deploy time via a scoped IAM role that can only read that one secret.
- App port exposure: only the ALB can reach EC2 on the app port. SSH is the only other open door, and only from your IP.

## Cost optimization

- `t3.small` (EC2) and `db.t3.micro` (RDS) - smallest practical burstable sizes for a demo/assignment workload.
- `db_multi_az = false` - Multi-AZ roughly doubles RDS cost; not needed outside production HA requirements.
- No NAT Gateway (~$32/month saved) - not needed since only RDS sits in private subnets.
- `skip_final_snapshot = true` on RDS - avoids paying for a lingering final snapshot after teardown.

## Backup strategy

RDS automated backups are enabled (`db_backup_retention_days`, default 7 days), covering point-in-time recovery for the database. EC2 has no automated backup - it's stateless application code pulled fresh from Docker Hub on each deploy, so redeploying (not restoring) is the recovery path for the instance itself.
